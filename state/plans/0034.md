# Plan — cycle 34 (architect, saved verbatim, X-012)

UNIT: R-6a, the physics half of metering. Physics gets a system-reported cost ledger (`POST /metering/usage`, runtime role only, cumulative per key, one key belongs to one agent). Metered cost replaces an agent's self-reported cost in the metrics. The Runtime gets a `FakeProvisioner` and `sync_costs`, which posts every fake dollar to the agent it belongs to. — R-6 (first slice; absorbs nothing else) — serves: EC4 "Every LLM dollar of the run is attributed to an agent via system-reported cost (or the fake provider in tests)". This does half of it and does not tick it. Also serves M4, and Era II's "leaderboard ranks by … system-reported costs".

That physics law has to exist before the gate can let a metered mind wake (R-6b). B-053, B-054 and R-4b-2b move no criterion.

DESIGN:
1. **`app/limits.py`**
   - `MAX_METERED_USD_MICROS = 10**12` ($1M; well below 2**53).
   - `KEY_REF_PATTERN = r"^[a-z0-9][a-z0-9_-]{0,63}$"`. A `key_ref` is an opaque label. It is never a key and never a key hash.
2. **`app/registry/permissions.py`**
   - New `Action.REPORT_METERED_COST = "report_metered_cost"`.
   - Grant it only to `AgentRole.runtime`; `system` keeps it through `frozenset(Action)`.
   - Not universal, not management. Update the runtime comment, which currently says it "does nothing a participant does": a metering row is physics' attestation about another agent, never activity of the runtime.
3. **`app/ledger/events.py`**
   - `EVENT_COST_METERED = "cost_metered"` with payload `{agent_id, pod_id, key_ref, usd_micros_total}`. Audit only: no reducer, no derived table.
   - Add `EVENT_COST_METERED: frozenset({"key_ref"})` to `AGENT_WITHHELD_FIELDS`. The key label is an operator fact (ADR-034 pattern).
4. **`app/metrics/metering.py`** (new). Reuse `append_event` and the error-class pattern of `app/metrics/reporting.py`.
   - `record_metered_usage(session, *, actor: Agent, agent_id: int, key_ref: str, usd_micros_total: int) -> Event | None`. Checks, in order:
     - unknown agent → `UnknownMeteredAgent` (404);
     - a target whose role is in `PHYSICS_ROLES` → `NotAFirmAgent` (422);
     - an earlier `cost_metered` event for this `key_ref` that names another agent → `KeyBoundElsewhere` (409);
     - a new total below the key's latest → `UsageDecreased` (409);
     - a total equal to the latest → returns `None`, writes no event (idempotent);
     - otherwise it appends the event, with `pod_id` = the target's registry `pod_id` (nullable).
   - Inactive agents are accepted: spend can land after a deactivation.
   - The check and the append run under a module `METER_LOCK` (`threading.Lock`), the same way `OMS_LOCK` is used. The gap across processes is the B-036 class; note it.
   - `metered_by_agent(session) -> dict[int, AgentMetered(pod_id, usd_micros)]` folds `cost_metered` events in id order (`Event.type` is indexed).
     - Each key's first event binds the key to its agent. A later event naming another agent is ignored and counted in `conflicts`.
     - Each key counts once, at its maximum total. Per agent, sum over its keys.
     - It sums totals, not deltas, so a double post can never double-count.
   - No table and no migration: the ledger is the store, so rebuildability holds by construction.
5. **`app/api/schemas.py`**
   - `MeteredUsageIn` (extra=forbid): `agent_id` (bounded like the other ids, `MAX_ID`), `key_ref` (str, `KEY_REF_PATTERN`), `usd_micros_total: StrictInt` in `0..MAX_METERED_USD_MICROS`. `StrictInt`, so `true` and `1.0` are refused.
   - `MeteredUsageOut`: `agent_id, key_ref, usd_micros_total, recorded: bool, event_id: int | None`.
6. **`app/api/metering.py`** (new router, prefix `/metering`, included in `app/main.py`).
   - `POST /metering/usage` with `require(Action.REPORT_METERED_COST)`; returns 200 `recorded` true or false.
   - Errors map to 404/422/409; commit or roll back as `app/api/reporting.py` does.
   - HALT → 423 through the existing middleware. Cumulative totals catch up after the halt lifts.
7. **MCP tool** `report_metered_usage` in `mcp_server` (the existing tool pattern). `tests/test_mcp_server.py` enforces it. No spec in `specs/` lists it.
8. **`app/metrics/service.py`**
   - `_cost_metrics(session, pod_id, metered)` takes `metered_by_agent` (read once per report, or once per leaderboard and passed down).
   - The law: an agent with **any** metered row is metered, and its `Cost` rows leave the authoritative total. An unmetered agent keeps its self-reports. Metered dollars go to the event's `pod_id`.
   - `CostMetrics` gains:
     - `self_reported_usd_cost: float` (every `Cost` row of the pod, as today);
     - `metered_usd_cost: float | None` (`None` if no agent in the pod is metered; `0.0` if metered at $0);
     - `metered_agents: int`;
     - `self_report_gap_usd: float | None` (metered agents' self-reports minus their metered cost; `None` if none is metered). This gap is the finding signal from 03 §4.2.
   - `total_usd_cost` becomes the authoritative figure. With no metered rows it is numerically unchanged.
   - `PodMetricsOut` and `LeaderboardRowOut` gain the fields. `cost_adjusted_pnl` and the ranking use the authoritative total.
9. **`runtime/metering.py`** (new). Imports only stdlib and `mcp_server.client.FundClient`/`FundAPIError`, as `runtime/lockstep.py` reaches physics.
   - `KeyUsage(key_ref, agent_id, usd_micros_total)` (frozen).
   - `Provisioner` Protocol: `usage() -> list[KeyUsage]`.
   - `FakeProvisioner`:
     - `create_key(agent_id, limit_usd_micros) -> key_ref` gives deterministic `fake-0001`, …;
     - `charge(key_ref, usd_micros)` refuses past the limit (`LimitExceeded`; this mirrors an OpenRouter credit limit) and refuses unknown keys;
     - `usage()` is sorted by `key_ref`. No secrets, no network.
   - `async sync_costs(provisioner, client) -> SyncReport(posted, unchanged, refused: list[(key_ref, status, detail)], halted: bool)`. Per key, `POST /metering/usage` with the cumulative total.
     - 423 → stop, `halted=True`;
     - 401/403 → raise (wrong key);
     - 404/409/422 → record and continue (one bad key never hides other agents' dollars).
10. **ADR-041** in `bible/07_DECISIONS.md`. Correct `03_WORLD.md` §4 item 2 ("as the `runtime` identity", not `system`).

INVARIANTS:
- No LLM call in `app/`. Time only through `append_event` and `ledger_now`. The dependency law holds: `runtime/metering.py` loads no `app` module beyond `{app, app.config, app.limits}` (the dynamic probe covers it).
- Permissions only in `permissions.py`. Every refused caller gets a 403 and a `permission_denied` event.
- Attribution comes from the event's `agent_id` and is bound per key at first use. A key never changes agent.
- Cumulative totals only; a key's total never decreases; a re-post is a no-op with no event; derived numbers come from maximum totals, never from sums of deltas.
- Money is integer micro-dollars in the ledger, converted to dollars only at the metrics boundary (`round_money` on the final total).
- Ledger rebuildability: there is no new table, and metrics after `rebuild_state` are equal.
- `null` not `0`: `metered_usd_cost` and `self_report_gap_usd` are `None` when no agent is metered.
- Every endpoint has an MCP tool.
- A pod with no metered rows gets exactly the old numbers.
- The gate is untouched: under any cap no spending mind wakes (EC6 holds).
- HALT refuses metering writes (423).

RISKS:
- **Old tests a new law may legitimately break** (findings, not things to fix): tests that pin the exact field sets of `PodMetricsOut`, `LeaderboardRowOut` or `CostMetrics`, or the role's permission set (`tests/test_runtime_identity.py` asserts the runtime role is exactly READ_HALT/READ_CLOCK/CONTROL_CLOCK). Each needs a note in the ADR, not a quiet edit.
- **Replay versus metering (decided in R-6b, recorded now).** A metered run's ledger will hold `cost_metered` rows that a $0 replay cannot produce. If sync runs between steps, ids shift and `compare-ledgers` (ADR-040, ids strict) fails. Never widen the comparison to make it pass. The likely answer is that sync runs only after the last step, so metering is a trailing block that the comparison law handles by type, by an ADR.
- **Pod drift.** Dollars go to the `pod_id` of each key's latest event. Agents do not change pods today; if a move endpoint ever exists, metering must split by delta.
- **Concurrency.** `METER_LOCK` covers one process only (B-036 class). The reader's first-binding rule and maximum-total rule keep a race from double-counting or rebinding.
- **Exploits.**
  - A firm agent gets no lever: it cannot post; its self-report cannot lower or raise its cost once it is metered; it cannot read `key_ref`.
  - A management mind can still see the self-report gap of other pods through metrics. That is intended data.
  - A stolen runtime key could forge costs. That is operator-level and the same trust as the clock (ADR-033).
  - Self-report spam (B-000n) is still unbounded, but no longer affects a metered agent's ranking.
- **Over-claiming.** This cycle does not tick EC4: no mind spends yet, and the gate is unchanged. Say so in the ADR and in STATE.

RED-TEAM: yes — the change touches `app/registry/permissions.py` (a new right), a new physics write path, and the ranking law. Targets:
- metering a rival or a physics identity;
- rebinding a key or lowering a total;
- `bool` and float coercion, and overflow;
- double-counting under re-post or race;
- self-report masking;
- `key_ref` leaking to agents;
- writes under HALT;
- the metrics reader fooled by events written straight into the ledger.

ADR: ADR-041 (R-6a; amends ADR-033 and 03 §4):
1. *Who posts system cost?* The `runtime` role, through a new narrow right `REPORT_METERED_COST`, not `system`. The Runtime process holds both, so a separate identity buys no seal, while `system` would give the sync job every right (prime rule: safer seal).
2. *Deltas or cumulative?* Cumulative per key in integer µ$: idempotent, catches up after a HALT, cannot double-count, and is exact.
3. *What does "overrides" mean?* Per agent: once metered, an agent's self-reports leave the ranking and stay as a cross-check (the gap).
4. *Where does it live?* In the ledger only. No table and no migration; the reader folds events.
5. *Open question for R-6b, answered now:* metering rows in a replayed ledger. Answer: sync after the last step only; the comparison treats a trailing `cost_metered` block by type, decided in R-6b's own ADR.
