DESIGN:
1. **`runtime/cli.py`: new `replay` subcommand.**
   - Flags: `--cassette PATH` (required), `--specs DIR` (required), `--input FILE`, `--days-per-step D`, `--max-tool-calls K`, `--server URL`.
   - **No `--steps` flag**: the step count comes from `Recording.steps`.
   - Usage phase (exit 2, nothing contacted), in this order:
     1. `load_specs`.
     2. `Recording.load(path)`. Turn `CassetteError` and `RecordingError` into `_Usage`.
     3. The loaded spec ids must equal `rec.spec_ids`, else `_Usage("the specs are not the recording's minds")`.
     4. `specs = [replay.as_cassette(s) for s in specs]`, then `registry.check_spec` on each. A contradiction becomes `_Usage`; this is how a spec with a model is refused ("cassette v1 cannot replay a model-bearing run: v2").
     5. The same range checks, `_read_input`, `_key` and `_loopback` that `_backtest` uses.
   - Put the flags and checks both commands share into one helper, e.g. `_common(args) -> (input, registrar_key, clock_key, server)`. Do not copy them.
   - Conduct with the existing `_conduct(...)`, extended with one keyword: `replay: Recording | None = None`, passed to `run_backtest(replay=...)` with `steps=rec.steps`. `check_clock`, then `declare_minds`, then `provision` stay in the current order. `declare_minds` on cassette specs declares `["cassette"]` (`lockstep.mind_kinds`).
   - Output: the same redacted JSON `{ended, reason, registered, run}`.
   - Exit codes: 0 only for `completed`; 1 for `diverged`, `refused`, `halted` or `error`; 2 for usage errors.
   - The module docstring says plainly that **exit 0 is not proof of an identical ledger**: run `fund-env compare-ledgers` against the recorded database.
2. **`runtime/lockstep.py::run_backtest`: the refusal law (NOTE 4).** Reorder the per-wake chain so that a replay ends the way a live run would at every wake a live run would stop:
   - `halted` → halted. Unchanged, still first.
   - `refused`:
     - if the reason is `no_identity` and `await _key_dead(mind.client)`:
       - live run: retire the mind and continue (unchanged);
       - replay: `diverged:<id>:<step>:<replay.divergence(step, record)>`. This stays `…:0:ended`, so the existing retirement test is untouched.
     - any other refusal → `refused`, `wake_refused:<id>:<reason>`, in both modes.
   - Any other end (`done`, `tool_budget`, `error`) during a replay → `replay.divergence` check, as today.
   - Do not touch the `decide_batch` calls, the H2 `min(tape.tool_calls, max_tool_calls)` clamp, or the calendar checks.
3. **`app/ledger/compare.py` (new, physics side, read-only).**
   - `ledger_rows(path: Path) -> list[tuple]`: open with `sqlite3.connect(f"file:{path}?mode=ro", uri=True)` and read `SELECT id, ts, actor_agent_id, type, payload_json FROM events ORDER BY id`. A missing file raises; it never creates one.
   - `compare(recorded, replayed) -> LedgerComparison(equal: bool, allowed: int, first_difference: int | None, detail: str)`.
   - The law:
     - equal length, and every row equal **as raw text**, ids and ts included. This is stricter than EC2's "except ids/wall-clock". Any difference there is a finding;
     - with exactly one exception: the single `run_minds_declared` row in each ledger, at the same index. Its id, ts, actor and type must be equal. The replayed payload must be exactly `{"minds": ["cassette"]}`. The recorded payload must be a `{"minds": [...]}` of valid kinds (`app.run_clock.MIND_KINDS`);
     - if both declare `cassette` (a replay of a replay), the rows are simply equal.
   - Derived tables are not compared: they rebuild from the ledger. Say so in the docstring.
   - The Runtime stays ledger-blind. It does not import this module, and nothing is added to the `runtime` role.
4. **`app/cli.py`: `fund-env compare-ledgers RECORDED_DB REPLAYED_DB`.** Prints one JSON object (the `LedgerComparison`). Exit 0 if equal with at most one allowed difference, 1 if different, 2 if a path is missing or unreadable or not a fund database (no `events` table). It is a CLI command, not an endpoint, so no MCP tool is needed.
5. **`scripts/smoke_run.py`.**
   - Turn the database setup and `serve` lifecycle in `backtest_check` into a helper you can call twice. Setup is the same `fund-env` sequence with `SMOKE_WORLD_KEY` and a new port.
   - Run 1: the existing `backtest` gains `--cassette tmp/desk.cassette.json`. New step: the cassette was written.
   - Run 2, on a fresh database: `fund-runtime replay --cassette … --specs specs/desk-month --input specs/desk-month/input.json`. Assert exit 0, `ended == completed`, `run.minds == "cassette"`, 10 wakes, every exchange's usage is zero, and no key in stdout or stderr.
   - Then `uv run fund-env compare-ledgers db1 db2`. Assert exit 0 and exactly one allowed difference.
   - Generalise `minds_check(db, kind)` to take the kind, and use it for both databases.
6. **ADR-040 in `bible/07_DECISIONS.md`.** It amends ADR-038. Also a `docs/` note only if it is short. The ADR states the X-006 answer below.

RISKS:
- **Ledger nondeterminism outside the minds.** Operator setup events (`seed-admin`, `seed-runtime`, `create-pod`) or `serve` startup may write a wall-clock ts, or something run-specific, into the ledger. If the smoke comparison fails there, that is a determinism finding: record it in the ADR and fix it at the source. **Never widen the allowed difference** to make it pass.
- **Old tests a new law may legitimately break** (findings, not fixes):
  - Any test that asserted a replay setup refusal reads `diverged:…:ended`. None is known; the retirement test keeps `:0:ended`.
  - Pins on `_conduct`'s signature, or a test counting `/me` calls during a replay. `_key_dead` now runs in replay mode on a `no_identity` refusal.
- **Over-claiming.** Replay exit 0 is not "identical ledger". Only `compare-ledgers` against the *original* database says that, and the cassette carries no ledger digest, so the recorded database must be kept. State this in the ADR and the CLI docstring.
- **Label hides a world change.** An in-world act (management moving or firing an agent) could make a replay end `refused:identity_mismatch` instead of `diverged`. The run still exits 1 and never `completed`; only the label differs. Accept it and record it in the ADR.
- **Exploits.** A cassette with forged replies and consistent hashes still replays inside the agent key's permissions. `compare-ledgers` is what catches it. A hostile, huge cassette still has no size cap (R-4b-2b). `compare-ledgers` reads attacker-chosen paths, but read-only. It must not follow a missing path into creating a database.
- **Smoke runtime grows** with a second database and server. Keep it sequential: stop server 1 before starting server 2, or use separate ports. Clean up both temp directories.

ADR: ADR-040 (R-4b-2a; amends ADR-038):
- (1) *Who compares the ledgers?* Physics' operator command `fund-env compare-ledgers`, read-only. The Runtime stays ledger-blind (boundary law; the `runtime` role has only READ_HALT, READ_CLOCK and CONTROL_CLOCK). Under the prime rule this keeps the seal.
- (2) *Is a setup refusal during a replay a divergence?* No. A replay ends the way a live run would at every wake a live run would stop. "Diverged" is kept for wakes that ran, and for a retirement, which a live run absorbs silently but a replay cannot. This closes NOTE 4.
- (3) *Which parameters does a v1 replay take?* Steps from the recording; input, days per step and max tool calls from flags. A mismatch is caught: the input as `world` at turn 0, the days as `calendar`, the budget through `tool_budget` (H2) or `ended`. Recording them is cassette v2 (R-4b-2b).
- (4) *Strict or EC2-loose comparison?* Strict: raw text, ids and ts included. That is the more honest measurement; a difference is a finding.
- **X-006 answer (record it in the ADR).** The replay compares: request hashes (prefix transcript, tools, model, so identity and input as well), each wake's `ended` and `tool_calls`, the calendar, the step count, the spec ids, and that no mind was retired. It **never compares**:
  - the recorded replies (taken from the tape, never hashed);
  - usage and cost (zero by design);
  - `redactions`;
  - each wake's `reason` and `tool_failures`;
  - trailing tool results after the last turn of a `tool_budget` wake;
  - the outcome's `registered` and `reason`;
  - spec fields that appear in no request (budget, wake policy; in v1 the model);
  - the ledger itself. Only `compare-ledgers` against the recorded database checks it.
